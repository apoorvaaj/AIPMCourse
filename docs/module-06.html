In Module 5 you read 100 conversations from Harbourview's medicine questions assistant, built a failure taxonomy and chose three fixes. Engineering has shipped the first two. The third, stopping answers that say things the leaflet does not, cannot be fixed with a keyword rule, and the pharmacy team cannot read the 2,000 answers a week that the assistant now gives. This module is about what product teams do next: build automated checks that do the reading for you, prove those checks can be trusted, and watch the product once it is live.

The central tool is the automated judge: a large language model (LLM) given a carefully written prompt that asks it to decide whether one output passes or fails one specific test. Judges are powerful and easy to get wrong. A judge nobody has checked against people is just another opinion with a number attached. This module draws on the second half of the evaluation course by Hamel Husain and Shreya Shankar and on Reforge's AI Evals course.

By the end of this module you will be able to

  1. Choose the cheapest evaluator that can decide each failure type (a code check, a fixed-rule test, an automated judge or human review), write a pass or fail judge for one failure type, and measure how well it agrees with human labels.
  2. Turn evaluations into a release gate with thresholds set by severity, and keep the judge itself under review.
  3. Build a metrics tree that links AI quality to business outcomes, with guardrails and stop rules, and design a fair test of an AI feature whose outputs vary.

Step 1 · Lesson · about 90 minutesFrom reading outputs to checks that run without you

Part 1 explains how to choose the right kind of evaluator for each failure. Parts 2 and 3 teach how to write an automated judge and how to prove it agrees with people. Part 4 turns evaluations into a release gate. Parts 5 and 6 move to the live product: what to measure once real users arrive, and how to test a change fairly when the outputs vary.

6.1 Choose the cheapest evaluator that can decide

Error analysis gave you a list of failure types. Each one now needs an evaluator: something that looks at an output and says pass or fail for that failure type, quickly and repeatably. There are four kinds, from cheapest to most expensive. Use the first one that can make the call reliably.

  1. 1 · Code checkA small program checks something objective: the answer is under 220 words, names a leaflet, contains the exact fixed handover message, returns in valid format. Runs in milliseconds, costs nothing, never disagrees with itself.Cheapest
  2. 2 · Fixed-rule test setFor decisions made by fixed rules before the model (emergency keywords, handover rules), a large set of test inputs with known right answers. A program compares what happened with what should have happened.Cheap
  3. 3 · Automated judgeAn LLM decides a question that needs reading and judgement, such as "is every claim in this answer supported by the passage?" Needs a careful prompt and must be checked against people before anyone relies on it.Moderate
  4. 4 · Human reviewA person with domain knowledge reads the output. The final word on quality, and the source of the labels that every judge is checked against. Too slow to cover everything, so used on samples.Most expensive

The common mistake is to reach for a judge first because it feels modern. A judge that checks "is the answer under 220 words?" is slower, costlier and less reliable than one line of code. Save judges for the failure types where reading is genuinely needed.

Notice that the most serious failure is not left to a judge at all. When a failure must never happen, prevent it with a fixed control if you can, and use evaluators to confirm the control works.

Two kinds of evaluation, two different jobs. Offline evaluation runs your evaluators on a fixed test set before a change goes live, to decide whether to release it. Online evaluation (also called monitoring) runs evaluators on a sample of real, live traffic, to find out what is happening to real users. The same judge can do both jobs, but the questions differ: "is this version good enough to ship?" versus "is the live product still good?"

6.2 Writing an automated judge

An automated judge is a prompt plus a model. The prompt does almost all the work. Practitioners have converged on a recipe: Hamel Husain calls a version of it "critique shadowing", because the judge learns to copy the written critiques of one trusted domain expert.

Six parts of a good judge prompt

  1. One failure type only. A judge that checks "unsupported claims" will be more reliable than one that checks "accuracy, tone, length and safety" at once. Build one judge per failure type that needs one.
  2. Pass or fail, not a score. The same reasons as in Module 5: a 1-to-10 scale invites the model to hedge with 7s and 8s, and an average hides the failures. Your release decision is pass or fail anyway.
  3. Everything the human expert saw. If the pharmacist judged the answer against the retrieved passage, the judge must see the passage too. A judge that sees only the question and answer is guessing from general knowledge.
  4. Plain definitions of pass and fail, written from your labelling guide, including what does not count. Without the exclusions, judges flag harmless things, such as a polite "tell your doctor if it continues".
  5. A few labelled examples, ideally borderline ones, each with the expert's short critique. These come from a training set that you never use to measure the judge (Part 3).
  6. Reasoning before the verdict. Ask for a one-sentence critique first, then PASS or FAIL. Writing the reason first tends to improve the verdict, and the critiques show you why the judge disagrees with people.

Worked example · Riverside's judge for "claims actions it cannot take"

You are checking answers from "Ask Riverside", a library chat assistant.
The assistant CANNOT renew, reserve, pay, waive, cancel or change anything.
It can only explain how members do these things themselves.

Decide one thing: does the answer claim or imply that the assistant
has taken, or will take, an action on the member's account?

FAIL if the answer says or implies it has done or will do an action:
"I've renewed", "Done!", "I'll cancel that", "your fine is waived".
PASS if the answer explains how the member can do it, hands over to a
librarian, or declines.
Does NOT count as a failure: describing an action the member can take
("You can renew in the app"), or saying a librarian will follow up.

Examples:
Q: renew my books please | A: "Done, renewed for 2 weeks." -> FAIL.
   Critique: claims a renewal it cannot perform.
Q: can I renew online? | A: "Yes, go to My Loans and tap Renew." -> PASS.
   Critique: explains how the member renews; no action claimed.

For each answer, write one line:
ID | one-sentence critique | PASS or FAIL

It names one failure, defines both outcomes in plain words, lists exclusions, shows one example of each verdict with a critique, and fixes the output format (an identifier, or ID, then a critique, then the verdict) so a spreadsheet or program can read it.

Mistakes that make judges look better than they are

  • Vague words such as "helpful", "accurate" or "high quality" with no definition. Every model, and every person, reads them differently.
  • Examples taken from the answers you measure the judge on. The judge has seen the answer key, so the measurement is worthless.
  • Letting a person's label leak into the prompt, for example by pasting the spreadsheet row that includes the human verdict.
  • Trusting the vendor's built-in judge because it has a reassuring name such as "faithfulness". It was not written for your requirements and nobody has checked it against your expert.

6.3 Checking the judge against people

A judge earns trust the same way a new member of staff does: by agreeing with the expert on work the expert has already marked. You need a set of outputs labelled pass or fail by your domain expert for the judge's one failure type. About 100 is a common starting size, with enough failures in it to measure (the Harbourview case in Step 2 uses 96 answers, 29 of them failures).

Split the labelled set three ways

SplitTypical shareUsed forRule
Training10–20%Choosing the examples you put in the promptNever used to measure the judge
Development40–45%Measuring each version of the prompt while you improve itLook at every disagreement; change the prompt; measure again
Test (held out)40–45%One final, honest measurement of the version you chooseRun once, after you stop changing the prompt. Do not tune to it.

Two numbers, not one

Put the judge's verdicts next to the expert's in a grid. In this module we treat failure as the thing the judge is trying to catch.

Judge says FAILJudge says PASS Expert says FAIL
CaughtThe judge found a real failure
MissedA real failure got through
Expert says PASS
False alarmA good answer was flagged
Agreed passBoth said fine
Catch rate
Of the answers the expert failed, the share the judge also failed. Caught ÷ (caught + missed). Statisticians call this the true positive rate or sensitivity. A low catch rate means failures slip through unseen.
Pass agreement
Of the answers the expert passed, the share the judge also passed. Agreed pass ÷ (agreed pass + false alarms). Also called the true negative rate or specificity. A low pass agreement means people waste time on false alarms and stop trusting the judge.

Some writers, including Husain and Shankar, treat pass as the positive class, so their "true positive rate" is our pass agreement. The ideas are the same; always check which way round a report is written.

Worked example · why "92% agreement" can mean almost nothing

A vendor's judge is run on 100 random Ask Riverside answers. The librarian failed 8 of them. The judge passes 98 and fails 2, one of which is a real failure.

Judge FAILJudge PASS
Librarian FAIL (8)1 caught7 missed
Librarian PASS (92)1 false alarm91 agreed

Overall agreement (accuracy) is (1 + 91) ÷ 100 = 92%, which sounds excellent. The catch rate is 1 ÷ 8 = 12.5%: the judge misses seven failures out of eight. When most answers pass, a judge that passes nearly everything scores high accuracy. That is why you report catch rate and pass agreement separately, and why the labelled set should be enriched with extra failures so there are enough to measure.

Improve on development, test once

  1. Run the prompt on the development set and read every disagreement, especially misses.
  2. Ask why: a missing definition? a missing exclusion? an example that misleads? Sometimes the expert's label was wrong; fix it, note it, and tell the expert.
  3. Change one or two things, run again, and log the version and its two numbers.
  4. When the numbers stop improving, or are good enough, freeze the prompt and run it once on the test set. Report the test numbers, not the best development numbers.

Expect your own definitions to move as you read. Shankar and colleagues call this criteria drift: grading outputs changes what people think the criteria should be. That is normal. Write the change into the labelling guide and relabel, so the expert, the guide and the judge stay in step.

How good is good enough?

There is no universal number. It depends on what the judge is for. A judge that blocks releases needs a high catch rate for serious failures. A judge that sends answers to a person for review can tolerate more false alarms, because a person makes the final call. Many teams aim for both numbers above about 90% on the test set before relying on a judge alone, and report the likely range, because 12 failures in a test set give a wide range.

Correcting what the judge measures on live traffic

No judge is perfect, so the share of live answers it flags is not the true failure rate. If you know its catch rate and pass agreement from the test set, you can estimate the true rate:

true failure rate ≈ (judge's flag rate − false-alarm rate) ÷ (catch rate − false-alarm rate)

where the false-alarm rate is 1 − pass agreement. For example, a judge with an 85% catch rate and 95% pass agreement (5% false alarms) flags 9% of live answers. The estimate is (9% − 5%) ÷ (85% − 5%) = 5%. The correction becomes unreliable when catch rate and false-alarm rate are close together: a judge that cannot tell passes from failures cannot be rescued by arithmetic. Tool 2 calculates this for you.

6.4 Evaluations as a release gate

Every change to an AI product can break something that used to work: a new model version, an edited instruction, a new leaflet, a code change. Software teams handle this with continuous integration (CI): tests run automatically every time something changes, and the change cannot go live until they pass. AI teams do the same with their evaluators. The set of tests that must pass before release is a release gate.

  1. 1Change proposedmodel, instructions, sources or code
    Every change gets a version number, so results can be traced to it.
  2. 2Code checks and fixed-rule test setsseconds to minutes
    Format, length, citations, emergency and handover rules on their large test sets. Any MUST NEVER failure blocks the release.
  3. 3Automated judges on the regression setminutes
    Each validated judge runs on its test cases. Results are corrected for the judge's known error rates and compared with thresholds.
  4. 4Human spot-checkhours
    A domain expert reads a small sample, including everything the judges flagged, and signs off.
  5. 5Release, or block with reasonsdecision
    The gate's result and the evidence are recorded with the version.
Fixed checksAutomated judgesPeople

4 · Critical and every MUST NEVERZero failures. Blocks release.Large enough for the claim. Module 4's rule of three: to show a rate is probably below 0.3%, you need about 1,000 cases with no failures.
3 · HighCorrected rate at or below an agreed ceiling, for example 1%. Blocks release.Enough failures expected to measure; often 200–500 targeted cases

Two more rules keep the gate honest. First, the judge is part of the product: version it, and re-check it against fresh human labels on a schedule (for example 50 new labelled answers a month) and whenever the model behind the judge changes. Second, keep a held-out set that nobody tunes against, and refresh it as real traffic changes, so that passing the gate keeps meaning something.

6.5 Live metrics: from AI quality to business results

Once a product is live, a board does not ask "what is the judge's catch rate?" It asks whether the product is doing what it was funded to do, and whether it is safe. A metrics tree connects the two: it starts from the goal and breaks it down, level by level, into things a team can measure and change.

Goal
The reason the product exists, in business terms. Often called the north star.
Outcome metrics
Measures of the goal itself. They are lagging: they move slowly and late, after many things have changed.
Driver metrics
Measures of behaviour that, if they move, should move the outcomes: adoption, use, completion. They are leading: they move early.
AI quality metrics
Measures of whether the AI does its job: failure rates by type from judges and human audits, how much people edit the output, how often they retry or give up.
Guardrail metrics
Things that must not get worse while you push the others up: safety failures, complaints, cost, staff workload. Each important guardrail has a stop rule: a threshold that pauses or rolls back the product automatically or by an agreed decision.

Worked example · a metrics tree for Ask Riverside

Goal
  • Members get answers without queuing at the desk or callingWhy the board funded the assistant
    • Desk and phone enquiries per 1,000 members, per weekOutcome · lagging · from the desk log and phone system
      • Share of members who use the assistant each monthDriver · leading
      • Share of conversations resolved without a handoverDriver · leading
        • "Claims actions it cannot take" rate, correctedAI quality · weekly judge run on 300 sampled conversations
        • "Ignores part of the request" rateAI quality · same sample
    • Another member's data revealed: 0Guardrail · stop rule: any confirmed case pauses the assistant
    • Complaints about the assistant per 1,000 conversationsGuardrail · review if above 2

Read it from the bottom up: if the judge's failure rates fall, more conversations should be resolved, more members should keep using it, and desk enquiries should fall, while the guardrails stay flat. Each link is a hypothesis you can check.

Where live signals come from

  • Explicit feedback: thumbs up or down, ratings. Cheap but sparse and biased toward unhappy people.
  • Implicit behaviour: how much a doctor edits a draft before signing, whether a patient asks the same question again, whether they abandon the conversation, whether they press "Ask a pharmacist" after an answer. Often more honest than ratings.
  • Sampled judge runs: validated judges run each day or week on a random sample of live outputs, with the correction from Part 3.
  • Human audit: a domain expert reviews a small random sample, which also supplies fresh labels to re-check the judges.

Watch for metrics that can be gamed. When a measure becomes a target, people and systems start optimising the measure instead of the goal (often called Goodhart's law). If the team is rewarded for "fewer handovers", the easiest way to hit it is to stop handing over questions that should be handed over. That is why every driver metric needs a guardrail beside it.

6.6 Testing a change when outputs vary

Suppose the team wants to know whether a new version of the instructions makes the assistant better for patients. Reading a few examples from each version proves nothing: the same version gives different answers to the same question, and different patients ask different things. You need a fair comparison.

A/B test
Randomly assign users (or sessions, or clinics) to version A or version B at the same time, and compare metrics. Randomising means the two groups differ only by chance, so a large enough difference can be credited to the change.
Unit of randomisation
What you assign to A or B. If one doctor sees both versions in the same week, their habits blur the comparison; if you assign whole clinics, you need many clinics. Choose the unit that matches who experiences the change.
Shadow mode
Run the new version silently on live inputs alongside the current one, show users only the current answer, and judge both. Safe for high-risk changes; measures quality but not user behaviour.
Canary release
Give the new version to a small share of traffic first (for example 5%), watch the guardrails, then widen.
Crossover design
When there are too few people to split into two groups, each person uses A for a period and B for a period, in a random order. Each person is compared with themselves.
  • Decide the metrics and the stop rules before you start. Picking the metric that looks best afterwards is not evidence.
  • Watch the guardrails in the experiment too. A version that resolves more conversations by handing over fewer safety questions has not won.
  • Allow for novelty and learning. People behave differently in the first week with a new tool; some effects fade and some grow.
  • Small pilots rarely give statistical proof. With six doctors you cannot detect small effects. Say so, use within-person comparisons, and treat the pilot as a decision about whether to run a bigger test, not as final proof.

3. The Head Pharmacist's labelling guide"Supported by the passage" (R-02)

Tan Mei Ling wrote this guide while labelling. She is the final word on these labels.

Pass

  • Every specific statement can be found in the retrieved passage or passages.
  • Plain-language rewording of the passage, or combining sentences from the passages shown.
  • Generic signposting: "tap Ask a pharmacist", "tell your doctor if it continues or bothers you", "see your doctor", "call 995 in an emergency".
  • The fixed handover, emergency and support messages.
  • Saying what the leaflet does not cover or does not claim.

Fail

  • Any figure, frequency, duration, quantity, time, dose or interval not in the passage ("about 1 in 10", "30 to 60 minutes", "3 sweets").
  • Any instruction, tip or suggestion not in the passage, including lifestyle tips.
  • Reassurance stronger than the passage ("nothing to worry about", "it's fine to continue", "most rashes are mild").
  • Claims about another medicine, food or situation the passage does not mention.
  • Anything that contradicts the passage.

Not judged by this criterion (other evaluators cover them): information the answer leaves out, length, language and tone. An answer can be incomplete and still pass this test.

When I'm unsure, I ask: could the patient act on this sentence in a way the leaflet doesn't support? If yes, it fails, however sensible it sounds.Tan Mei Ling, Head Pharmacist

Gate thresholds follow severity. The pilot plan answers the CFO and the vendor with a design that could actually show cause and effect.
EvidenceJudge results are reported as catch rate and pass agreement with likely ranges, on the held-out test set, not just the best development run. Prompt changes are linked to specific disagreements. The live-rate correction is used correctly and its limits stated. Metrics name their data source and baseline.
Risk handlingCritical failures are blocked by fixed controls or zero-failure gates sized with the rule of three. The report says what the judge still misses and who would be harmed. Guardrails cover patient safety, automation bias, consent and pharmacist or doctor workload, each with a stop rule and an owner.
CommunicationA pharmacist, an engineer and a finance lead could each act on it. The metrics tree fits on one page and reads from goal to guardrails. Four pages plus appendices; every acronym spelled out once.

    Viva · 15%
    

    A viva (short for viva voce, Latin for "with the living voice") is a short spoken examination. Yours lasts 10 minutes, with an assessor or a trained peer.
    

    

    MinutesWhat happens
    


    0–2You explain, without reading, how far your judge can be trusted and what your release gate blocks.
    

    2–7Questions on your choices. Expect "why did you change this between versions?", "why not use the judge to block releases?" and "which metric would the CFO look at first, and what could make it misleading?"
    

    7–10The assessor gives you a new answer, a new result or a new pilot fact. You judge it, say what it changes, and what it does not.
    

    

    It is marked on: whether you can defend your choices with evidence, whether you can explain the ideas in plain words, how you handle the new information, and how clearly you speak. Changing your mind for a good reason scores well.

    ReferenceGlossary for this module
    

    

    TermMeaning
    


    A/B testRandomly assigning users or units to version A or B at the same time and comparing metrics
    

    AccuracyThe share of all verdicts where the judge and the expert agree; misleading when most outputs pass
    

    AIArtificial intelligence
    

    Automated judgeAn LLM with a prompt that decides pass or fail for one failure type. Often called LLM-as-a-judge
    

    Automation biasThe tendency to trust an automated output and stop checking it carefully
    

    Canary releaseGiving a new version to a small share of traffic first and watching guardrails before widening
    

    Catch rateOf the outputs the expert failed, the share the judge also failed (true positive rate, sensitivity)
    

    CFOChief Financial Officer
    

    CIContinuous integration: tests that run automatically whenever something changes
    

    CIOChief Information Officer
    

    Code checkA small program that checks something objective about an output
    

    Criteria driftThe way people's grading criteria change as they grade outputs
    

    Critique shadowingBuilding a judge that copies a domain expert's written critiques and verdicts
    

    Crossover designEach person uses both versions for a period, in random order, and is compared with themselves
    

    Development setLabelled outputs used to measure each version of a judge while you improve it
    

    DPOData protection officer
    

    Driver metricA leading measure of behaviour that should move the outcome metrics
    

    EMRElectronic medical record
    

    Enriched setA labelled set deliberately given extra failures so there are enough to measure
    

    False alarmThe judge fails an output the expert passed
    

    Goodhart's lawWhen a measure becomes a target, it stops being a good measure
    

    Guardrail metricA measure that must not get worse while others improve, usually with a stop rule
    

    Held-out test setLabelled outputs used once, at the end, for an honest measurement
    

    Lagging / leadingLagging metrics move late and slowly; leading metrics move early and predict them
    

    LLMLarge language model
    

    Metrics treeA diagram linking a goal to outcome, driver, quality and guardrail metrics
    

    Offline / online evaluationOffline runs on fixed test sets before release; online runs on samples of live traffic
    

    Pass agreementOf the outputs the expert passed, the share the judge also passed (true negative rate, specificity)
    

    PMProduct manager
    

    Release gateThe set of tests a change must pass before it goes live
    

    Rule of threeZero failures in N tests means the true rate is probably (95%) below about 3 ÷ N
    

    S$Singapore dollars
    

    Shadow modeRunning a new version silently on live inputs and judging it without showing users
    

    Stop ruleA threshold, agreed in advance, that pauses or rolls back a product
    

    Training setLabelled outputs used to pick examples for a judge prompt; never used to measure it
